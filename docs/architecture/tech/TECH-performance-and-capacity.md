# Sandbox 性能设计与容量验证

Status: active

Owner: SDKWork Runtime Platform

Updated: 2026-09-22

Parent: [SDKWork Sandbox Technical Architecture](TECH_ARCHITECTURE.md)

Specs: `ARCHITECTURE_DECISION_SPEC.md`, `PERFORMANCE_SPEC.md`, `TEST_SPEC.md`, `QUALITY_GATE_SPEC.md`, `OBSERVABILITY_SPEC.md`, `SECURITY_SPEC.md`, `RUST_CODE_SPEC.md`, `CACHE_SPEC.md`

本分片定义 Sandbox 的性能设计约束、性能与容量目标、以及证明这些目标所需的测量方法。产品侧验收口径见 [PRD-roadmap.md](../../product/prd/PRD-roadmap.md)。

**全部数值都是工程目标，不是已实现承诺。** 在参考硬件、Template、工作负载与统计方法被记录前，任何数值不得写入 Release Evidence。

## 1. 性能设计原则

### 1.1 零拷贝优先

文件与网络数据路径优先使用内存映射、零拷贝发送与内核旁路拼接机制，避免在用户态反复复制缓冲区。任何需要“先读入内存再整体写出”的实现都必须给出理由，并通过基准测试证明其成本可接受。

### 1.2 异步但不阻塞

运行时使用 Tokio 多线程模型，但 CPU 密集型工作必须放到专用工作线程，**禁止阻塞异步运行时**。禁止通过增加线程数量解决并发问题（`PRD.md` 非目标）；线程数是需要基准测试确定的参数，不是调节旋钮。

### 1.3 异步 I/O 必须基准测试后选用

异步块 I/O 在 NVMe 并行请求场景具备性能潜力，但设备创建会引入额外延迟。因此不能无条件使用：

| 路径 | 策略 |
| --- | --- |
| 低延迟快速路径 | 同步 I/O 或内存映射 |
| 高吞吐路径 | 异步 I/O |

该选择必须由基准测试决定，而不是由架构偏好决定。

### 1.4 内存与连接复用

高频路径禁止频繁分配与释放。进程、RPC、网络、文件、快照路径必须使用对象池、slab 或缓冲区池。以下资源必须池化：元数据数据库、协调服务、对象存储、节点间 RPC、Template 存储。

### 1.5 锁与数据结构

高频路径尽可能使用原子操作、并发映射与无锁队列，避免全局互斥。**特别禁止全局 Sandbox 锁。**

### 1.6 调度复杂度

调度与查找必须在 `O(log n)` 量级完成，**禁止 `O(n)` 扫描全部 Sandbox**。允许的数据结构形态：优先队列、资源索引、租户队列、节点队列。任何需要遍历全部实例的判定都必须在构建期或增量维护阶段预先聚合。

### 1.7 背压与公平

- 资源不足时必须**排队并背压**，而不是无限创建。队列必须支持优先级、截止时间与租户权重。
- 租户之间使用加权公平队列，防止一个大租户的十万级任务把小租户完全饿死。
- 节点继续创建新工作负载前必须满足准入条件（CPU、内存、磁盘 I/O、网络均在阈值之下）；不满足时由调度选择其他节点，而不是超卖。

### 1.8 可观测性即设计输入

指标必须是低基数、可聚合、可长期保留的；高频路径的埋点不得成为瓶颈。禁止使用原始租户、会话或节点标识作为指标标签。

## 2. 性能目标

| 场景 | P50 | P95 | 说明 |
| --- | --- | --- | --- |
| 命名空间沙箱创建 | 小于 10 ms | 小于 30 ms | 热路径 |
| microVM 预热恢复 | 小于 100 ms | 小于 300 ms | 需真实 KVM 与 Snapshot 证据 |
| 控制面创建 API | 小于 50 ms | 小于 150 ms | 含准入与预约 |
| 本地文件读/写 | 接近宿主文件系统 | — | 相同硬件与相同文件规模下比较 |
| 代理出网吞吐 | 大于宿主带宽的 80% | — | 相同网络条件下比较 |

补充约束：

- 命名空间沙箱恢复的 P95 目标与创建同为 30 ms。
- CPU 开销目标：相对裸机同工作负载基线小于 5%。
- 热分配时延与冷启动时延必须**分开统计**，不得合并报告，也不得用热路径数据代表冷启动。

## 3. 并发与容量目标

| 维度 | 目标 | 前置条件 |
| --- | --- | --- |
| 单节点轻量执行环境 | 万级 | 需明确“轻量”对应的 Assurance 与资源档位 |
| 单节点活跃强隔离实例 | 千级 | 需真实 KVM 容量证据 |
| 集群节点规模 | 百级 | 需控制面与调度压测 |
| 集群执行环境总量 | 百万级 | 工程目标；由 Benchmark 修正 |
| 单集群控制面吞吐 | 十万级请求/秒 | 创建、暂停、恢复、删除需可水平扩展 |

这些数字全部属于工程目标。在完成测量前，它们只用于指导架构方向（共享优先、避免逐实例独占），不得作为对外容量承诺。

## 4. 资源目标

| 对象 | 目标（工程目标） |
| --- | --- |
| 空闲轻量执行环境 | 内存占用小于 10 MB |
| 预热 Runtime | 内存占用尽可能小于 20 MB |
| microVM | 按 Guest 内存、vCPU、内核与运行时动态分配，不做统一声明 |

资源目标必须按运行模式分别测量与报告。不得用最轻模式的数据代表强隔离模式，也不得用单实例数据乘以节点数推导节点容量（必须实测并发下的实际占用）。

## 5. 基准套件与测试矩阵

必须建立独立基准套件，覆盖：创建、启动、暂停、恢复、Fork、删除、文件系统、网络、进程、Snapshot、Template。并发档位至少覆盖百、千、万、十万。

测试矩阵：

| 维度 | 取值 |
| --- | --- |
| CPU | 4 / 8 / 16 / 32 / 64 / 128 核 |
| 内存 | 32 / 64 / 128 / 256 GB |
| 磁盘 | SATA / SSD / NVMe |
| 网络 | 1G / 10G / 25G |

每条基准结果必须同时记录：机器规格、内核版本、虚拟化能力、Template 版本、Artifact 元组、样本量、并发档位与统计方法。缺少任一要素的结果不得作为门禁证据。

## 6. 压测记录指标

必须记录：P50、P90、P95、P99、Max、错误率、CPU、内存、IOPS、带宽、上下文切换、页缺失。

分位数必须来自真实采样而不是插值估算；错误率必须区分“策略拒绝”与“系统故障”，二者不得合并为同一指标。

## 7. Chaos 测试矩阵

必须覆盖以下故障并验证系统进入可恢复的显式状态：
节点崩溃、网络故障、存储故障、协调服务故障、元数据数据库故障、对象存储故障、执行环境崩溃、Agent 崩溃、内存耗尽、磁盘写满、CPU 耗尽。

要求：

- 每类故障必须验证：不产生双重活动所有权、不静默丢弃权威数据、不确定时隔离而不是继续。
- 恢复路径必须可重放、幂等、有界。

## 8. 安全测试矩阵

必须覆盖：容器逃逸、命名空间逃逸、文件系统逃逸、权限提升、系统调用过滤绕过、网络逃逸、云 Metadata 访问、宿主访问、跨租户访问。

要求：

- 跨租户访问测试必须覆盖元数据、对象存储、快照恢复、端口暴露与终端流五个面。
- 网络策略测试必须在真实内核与真实网络栈上执行，不接受仅在单元测试中模拟。
- 隔离等级声明与实际机制的一致性必须被验证：声明 `MicroVm` 就必须真的运行在 microVM 中。

## 9. 容量与性能门禁

- 性能与容量声明只有在参考环境、Template、工作负载与统计方法被记录后才可作为发布门禁。
- 任何未通过真实硬件基准测试的时延、并发或资源数字，都不得写入 PRD、Release Evidence 或对外材料。
- 容量不足时必须走背压与调度路径，禁止通过降低隔离等级或超卖容量来“解决”性能问题。
- 禁止通过增加线程数量解决并发问题，禁止通过增加容器数量解决隔离问题，禁止在高频路径使用全局锁。
